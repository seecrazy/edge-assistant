# ADR 0003: 温控与功耗分级降级

## 状态

已接受

## 背景

端侧推理的算力和发热限制比服务器严格得多。语音通话是持续性负载，连续 10 分钟以上推理和音频处理会触发系统温控，导致非受控降频：首 token 延迟突然上升、TTS 卡顿甚至 App 被系统杀死。

目标要求“连续通话 10 分钟后主动进入低功耗模式，避免温控降频”，但当前设计缺少可实现的降级策略。

## 决策

采用分级主动降级策略：

1. 定义 normal / warm / hot / critical 四级热状态，由系统热 API 与连续推理时长共同驱动。
2. 每级状态映射一组预定义降级动作（缩短回复、降帧、停用视觉、暂停推理），不允许任意组合。
3. 降级在 UI 上明确提示，恢复按迟滞规则逐级进行，避免状态抖动。
4. 降级事件写入本地指标，不上传。

设计细节见 `docs/design.md` §5.7。

## 备选方案

### 方案 A：不做主动降级，依赖系统温控

优点：
- 实现成本为零。

缺点：
- 用户感知到的是“越用越卡”和偶发崩溃，无法建立稳定预期。
- 触发系统温控后降频幅度不受产品控制，语音延迟目标全部失效。

### 方案 B：仅响应式降级（检测到热警告后立即切最低功耗模式）

优点：
- 实现简单，状态少。

缺点：
- 体验断崖：一次警告直接砍掉视频和长回复能力。
- 恢复时机难判，容易在 normal 和最低模式之间振荡。

### 方案 C：分级主动降级（已选择）

优点：
- 降级幅度与热压力匹配，体验可预期。
- 迟滞恢复避免抖动。
- 动作集合固定，便于测试矩阵覆盖。

缺点：
- 需要维护状态机与各级动作的测试。
- 阈值需要按机型档位分别校准。

## 结果

选择方案 C。

### 正面影响

- 连续通话场景可以主动进入低功耗模式而不是被动等待系统降频。
- 降级对用户可见、可预期，符合“透明产品边界”原则。

### 负面影响与缓解

- 三档设备阈值不同：每档设备单独实测校准，初值由延迟预算推算。
- 降级状态机增加测试面：动作集合固定为枚举，纳入现有纯函数测试风格。
