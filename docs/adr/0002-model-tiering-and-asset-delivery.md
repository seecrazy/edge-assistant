# ADR 0002: 模型分级与资产分发

## 状态

已接受

## 背景

“模型随 App 一起安装”在实际移动生态中面临三个约束：

1. 主包体积受应用商店限制。
2. 低端设备无法运行大模型。
3. 不同芯片的 NPU/GPU/CPU 兼容性差异很大。

如果所有设备都安装同一个 3B 模型，会导致低端机不可用、高端机体验受限、下载转化率下降。

## 决策

采用设备分级 + 按档位分发模型的策略：

| 档位 | 设备条件 | 模型策略 |
|---|---|---|
| Flagship | RAM ≥ 12GB 且有 NPU | 3–4B，4-bit |
| Mainstream | RAM ≥ 8GB | 1.5–2B，4-bit |
| Entry | RAM < 8GB | 1B，4-bit |

分发方式：

- Android 使用 Play Asset Delivery 的 **install-time asset pack 作为默认**，实现“模型随 App 自带、开箱即用”；fast-follow asset pack 仅作为后续大模型热更新的可选通道。
- iOS 使用 On-Demand Resources，但模型资源标记为在首启安装流程中同步就绪（见 `docs/design.md` §3.2 流程 E）。
- 模型文件独立于业务代码，带版本号、hash 和能力清单。
- 安装或更新前校验完整性，失败回滚。
- 低端设备默认不下载超出硬件能力的大模型。
- 模型在系统安装 App 阶段随 install-time asset pack 一并落盘；首次启动 App 自动校验 SHA-256、激活并装载推理引擎，全程无网络请求、无用户操作。聊天等功能直接调用内置模型。

## 备选方案

### 方案 A：统一内置 3B 模型

优点：
- 版本管理简单。
- 产品能力一致。

缺点：
- 安装包超过 2GB，低端机不可用。
- 不符合应用商店分发最佳实践。

### 方案 B：首次启动后从服务器下载模型

优点：
- 主包最小。

缺点:
- 首次体验依赖网络。
- 与“随 App 一起安装”的目标不一致。

### 方案 C：设备分级 + 平台资产分发

优点：
- 兼顾体积、性能和首次可用性。
- 不同设备获得符合硬件能力的体验。

缺点：
- 需要维护多个模型版本和兼容性矩阵。

## 结果

选择方案 C。

### 正面影响

- 避免低端机强行运行大模型。
- 降低主包体积。
- 支持模型独立更新和回滚。

### 负面影响与缓解

- 多模型版本管理复杂：建立 `model_registry` 和能力标签。
- 测试矩阵增加：必须覆盖三档设备。
- 体验不一致：在产品中明确展示当前档位和能力限制。
